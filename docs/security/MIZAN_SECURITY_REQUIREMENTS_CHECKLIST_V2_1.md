# Mizan Security Strategy v2.1 — Prioritized Requirements Checklist

**Status:** Working checklist for a proposed strategy; this is not proof of implementation, certification, or deployment readiness.
**As-of evidence reviewed:** repository security documentation and the 11 Nov 2026 Mizan production UI audit.
**Named owners:** Not assigned; role placeholders below must be replaced by accountable people.
**Control status rule:** Only cite evidence directly observed in code/tests/reports. A repository design/test claim is not equivalent to live production enforcement. A UI label is not proof of backend enforcement.

## Status legend

- **Documented; not deployment-verified** — a repository document or test describes the control, but current target-deployment operation is not established.
- **Partial / gap remains** — some related mechanism/evidence exists, but the full requirement is not evidenced.
- **Not evidenced** — no sufficient implementation or test evidence was found in the reviewed sources.
- **Blocked in audited tenant** — production prerequisites or records were absent in the 11 Nov 2026 audit; this does not prove all deployments are identically configured.

## Proposed release gates

- **G0 — Architecture & ownership:** approved data flows, boundaries, threat model, named owners, failure behavior, and key/deployment decisions.
- **G1 — Secure core / sensitive-data pilot:** identity, tenancy, data protection, logging, key, upload, and fail-closed controls evidenced in the target environment.
- **G2 — External processing / RAG:** G1 passed; explicit transfer allowlist, signed Gate 1 records, retrieval isolation, AI-security and failure tests passed.
- **G3 — Model release / customer runtime:** signed provenance, anti-rollback, support-access, runtime and Golden Test controls passed.
- **G4 — Enterprise assurance:** recovery, incident exercises, independent assessment, vulnerability disclosure, and compliance evidence accepted.

Gates are proposed. Product and Security owners must approve their scope and dependencies before treating them as release criteria.

## Immediate recommended sequencing

1. **G0:** appoint role owners; reconcile asset/data-flow inventory; decide deployment/data boundaries, identity, keys, and failure semantics.
2. **G1:** close MZN-02 through MZN-07, MZN-09, MZN-13, and MZN-21 for the specific pilot environment; exercise negative tests and document exact evidence. The audited production tenant currently had no Gate 1 signed attestation, so it is not evidence of an approved-data flow.
3. **G2:** prove transfer/classification failure behavior, retrieval isolation, AI tool and injection defenses; only then enable external processing/RAG for approved synthetic or authorized test data.
4. **G3:** establish package/SBOM provenance, anti-rollback, support broker, runtime validation, Golden Tests, and containment guardrails before model/site activation.
5. **G4:** complete immutable/offline restore proof, incident tabletop, independent penetration test, vulnerability disclosure, and framework gap assessment before enterprise security claims.

## Evidence maintenance rules

- Keep source artifact path, commit/build identifier, environment, test command, run date, result, reviewer, and exclusions for every “verified” status.
- Reconcile contradictory documents before publication. In particular, strategy acknowledgement targets are placeholders while an incident runbook lists numerical response targets.
- Recheck production state separately from repository tests. Current audit evidence: production API health/readiness succeeded; Gate 1 approvals showed 0 masking runs, 0 pending reviews, 0 signed attestations; runtime test reported no active ready slot. A synthetic dataset v1 was frozen READY but was not approved.
- Do not mark a requirement “implemented” or “passed” solely because it appears in a proposed strategy, status report, architecture diagram, UI, or checklist.
